## 2. 权限与资产交接

接手人需要确认自己拥有以下权限，但不要互传个人账号密码：

- GitHub 仓库读写权限、Actions 运行权限和 production environment 使用权限。
- GitHub Actions secrets 的维护权限。至少包括 `SERVER_HOST`、`SERVER_USER`、`SERVER_SSH_KEY`、`GHCR_PROXY_SUBSCRIPTION`、`TENCENT_MPS_TEMPLATE_ID`。
- 生产服务器的独立 SSH 凭据。部署工作流要求用户为 `root`，并校验部署公钥指纹。
- 域名及 DNS、腾讯云服务器、对象存储/CDN、腾讯云 MPS、飞书/微信/短信等外部服务后台权限。
- 备份恢复私钥的离线保管位置和负责人。私钥不得放在仓库或服务器上。

当前已知问题：本机 `~/.ssh/config` 的 `myserver` 使用 `ubuntu` 和 `~/.ssh/id_ed25519`，截至 2026-09-20 连接返回 `Permission denied (publickey)`；而生产部署工作流使用 `root` 和专用部署密钥。交接时应为维护人员配置单独、可审计的运维密钥，不能从 GitHub Actions 导出或共用部署私钥。

建议 SSH 配置（仅示例，不提交私钥）：

```sshconfig
Host xiaobaic-production
  HostName 111.229.35.33
  User root
  IdentityFile ~/.ssh/<个人运维私钥>
  IdentitiesOnly yes
```

## 3. 首次接手盘点

登录后先只读检查，不要立即升级或清理：

```bash
hostnamectl
uptime
df -h
free -h
cd /opt/vitransfer/vitransfer-test
docker compose ps
docker images --digests
docker inspect -f '{{.Name}} {{.Image}} {{if .State.Health}}{{.State.Health.Status}}{{else}}{{.State.Status}}{{end}} restarts={{.RestartCount}}' \
  vitransfer-app vitransfer-worker vitransfer-postgres vitransfer-redis
curl --fail --silent --show-error https://mle6.cn/api/health
```

同时核对：

- `.env`、`docker-compose.yml`、`Caddyfile` 的属主和最近修改时间。
- 防火墙/安全组只开放必要端口；PostgreSQL 和 Redis 不应直接暴露公网。
- TLS 证书是否自动续期，域名和 DNS 的续费负责人是谁。
- 磁盘和 Docker 空间是否足够，是否存在异常增长的日志、镜像或临时文件。
- 最近一次成功部署的 commit SHA、Actions 运行链接和最近一次可恢复备份。

查看配置时只检查变量名，不在终端录屏、工单或聊天中输出变量值：

```bash
sed -n 's/^\([A-Z][A-Z0-9_]*\)=.*/\1/p' .env | sort
```

## 4. 标准更新流程

生产更新只从 GitHub Actions 的 `Xiaobaic CI and Manual Deploy` 发起。不要在服务器上 `git pull`，不要手工替换容器内文件，也不要把 `latest` 当作生产版本。

### 更新前

1. 确认工作区干净，改动经过评审，并明确本次发布的完整 commit SHA。
2. 在本地执行与 CI 一致的基础验证：

   ```bash
   npm ci --legacy-peer-deps
   npm audit --omit=dev --audit-level=high
   SKIP_ENV_VALIDATION=1 NEXT_PHASE=phase-production-build npm run build
   ```

3. 涉及关键业务时补做相应测试；涉及数据库迁移时，必须阅读迁移 SQL，判断是否可向后兼容。
4. 在发布窗口开始前记录 `docker compose ps`、当前镜像 ID、磁盘空间和健康接口结果。
5. 先生成并验证可恢复备份。仓库中的 `Backup production before server cancellation` 会导出数据库和配置并生成加密归档，但它的名称和用途偏向服务器下线；日常发布前使用时，也必须确认备份产物已成功保存且恢复私钥可用。
6. 明确回滚负责人、回滚目标版本和业务验证人。数据库破坏性迁移必须准备数据恢复方案，不能只依赖镜像回滚。

### 执行更新

1. 将已验证的 commit 推送到 `main`，等待自动 `Verify application` 成功。
2. 在 GitHub Actions 手动运行 `Xiaobaic CI and Manual Deploy`：选择 `main`，勾选 `confirm_production`。
3. 不要并行发起第二次生产部署。工作流已设置生产部署并发锁，但维护者仍应保持单一变更窗口。
4. 观察完整日志。工作流会以 commit SHA 构建 GHCR 镜像，在服务器保留回滚标签，重建 app/worker，并要求二者连续 30 秒健康且重启次数正常。

### 更新后

除了 Actions 变绿，还要完成业务冒烟：

```bash
cd /opt/vitransfer/vitransfer-test
docker compose ps
docker inspect -f '{{.Name}} {{if .State.Health}}{{.State.Health.Status}}{{else}}{{.State.Status}}{{end}} restarts={{.RestartCount}} image={{.Image}}' \
  vitransfer-app vitransfer-worker vitransfer-postgres vitransfer-redis
docker compose logs --since 15m app worker
curl --fail --silent --show-error https://mle6.cn/api/health
```

人工验证至少包括登录、打开一个现有项目、视频播放、上传或转码队列、分享页访问。若本次改动涉及飞书、微信、短信、MPS 或对象存储，再分别验证对应链路。

最后记录：发布时间、commit SHA、Actions 链接、执行人、验证人、迁移情况、异常与处理结果。建议写入 GitHub Release、部署 issue 或固定的发布记录，不只留在聊天中。

## 5. 回滚原则

部署工作流在健康检查失败时会自动恢复 `.env` 和更新前的 `vitransfer-mps:fast` 镜像，并重建 app/worker。出现以下任一情况应停止观察并回滚：

- app 或 worker 长时间不健康、持续重启。
- 健康接口失败，或核心业务路径不可用。
- 错误率明显升高、队列停止消费、上传/播放大面积失败。
- 数据异常或出现不可接受的安全风险。

自动回滚只覆盖应用镜像和本次 `.env` 变更，不会自动撤销已执行的数据库迁移，也不会恢复外部服务配置。对删除列、改写数据等破坏性迁移，恢复顺序应由迁移方案明确；不清楚时先停止 app/worker，保全现场和备份，不要反复启动不同版本。

需要人工处理时，先保留日志、当前镜像 ID和数据库备份，再按已验证的回滚版本操作。不要临场猜测标签，也不要清理当前及回滚镜像。

## 6. 日常维护习惯

### 每次改动

- 一次发布只解决一组相关问题；commit 小而可追踪，提交信息说明“为什么”。
- 配置变更和代码变更使用同一变更记录，写明新增/删除的变量名，但不写值。
- 新增环境变量时，同时检查 `.env`、Compose 的 app/worker 白名单以及 GitHub secrets。修改 `.env` 后必须 `--force-recreate`，单纯 `docker restart` 不会刷新容器环境。
- 不直接编辑生产文件。紧急操作若无法避免，事后必须当天回写仓库和变更记录，避免服务器成为唯一真相源。
- 不在高峰期做迁移、磁盘清理或基础设施升级；一次只变更一个层级。

### 每周

- 查看容器状态、重启次数、最近错误日志、磁盘/内存和队列积压。
- 检查健康接口及证书有效期，抽查上传、播放和分享链路。
- 确认最近备份成功且校验通过；备份失败必须当作故障处理。

### 每月或重大更新前

- 做一次恢复演练，至少验证加密归档能解密、数据库 dump 能在隔离环境导入。
- 复核 GitHub、云平台和第三方后台成员，移除离职或不再需要的权限。
- 轮换到期或泄露风险较高的密钥，并记录负责人和下次轮换时间。
- 更新本文中的服务器信息、外部依赖、恢复路径和联系人。

## 7. 常用排障顺序

1. 先确认外部健康接口和影响范围，不要先重启。
2. 查看 `docker compose ps`、容器健康状态和重启次数。
3. 查看 `app`、`worker` 最近 15 分钟日志，确认是代码、数据库、队列、存储还是第三方接口问题。
4. 检查磁盘、内存、时间同步和网络/DNS。
5. 对照最近一次部署 SHA 和配置变更记录。
6. 明确根因或至少保全证据后，再决定重启、回滚或恢复数据。

常用命令：

```bash
docker compose logs --since 15m app worker
docker stats --no-stream
df -h
docker system df
docker exec vitransfer-postgres pg_isready
docker exec vitransfer-redis redis-cli --no-auth-warning -a "$REDIS_PASSWORD" ping
```

最后一条命令不要直接在宿主机使用真实密码，以免进入 shell 历史；优先在容器中读取已注入环境变量，或仅依赖 Compose healthcheck。

## 8. 安全的清理规则

- 先用 `docker system df` 和 `docker images` 确认占用，再清理。
- 永远保留当前运行镜像和至少一个已验证的回滚镜像。
- 不执行未经逐项确认的 `docker system prune -a --volumes`；数据库、Redis 和上传目录都依赖卷。
- 不手工删除 `/var/lib/docker` 内容。
- 清理前确认备份成功，清理后再次检查容器、健康接口和磁盘空间。

## 9. 交接完成标准

只有下列事项均完成，才算交接完成：

- 接手人能用自己的账号登录 GitHub、云平台和生产服务器。
- 接手人能指出当前运行 commit，并独立完成一次测试环境或低风险生产发布。
- 双方共同完成一次备份验证和一次书面回滚演练。
- 域名、服务器、对象存储及第三方服务的续费和告警负责人明确。
- 所有密钥均通过密码管理器或平台 secret 交接，没有出现在本文或聊天中。
- 本文中的待核实项已用服务器实时信息更新，并由交接双方确认日期。
